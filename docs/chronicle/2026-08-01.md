### Chronicle

#### Decisions
- The preserve stage is generated into every pipeline unconditionally; only its *form* varies (inline for
  small sources, committed archive for large). A stage generated only when config asks for it reproduces
  the defect being fixed — a missing stage is one nobody notices is missing.
- The synthesis is a sibling output of the raw material, not an intermediate the evidence passes through.
  This removed the machinery that existed only to contain the old inversion: a primary/fallback tier
  ordering, an overlapping-tiers guard, and a transcript-survival check.
- Raw material renders to a scratch path outside the repo, is gated there, and moves into the archive only
  on pass. Ordering decides what "withhold" can mean: a file already in the committed tree can only be
  deleted, not withheld.
- Kept the `Sinks` stage that the spec's own numbering table omitted. Following the table literally would
  have silently dropped task routing from every newly generated graph.
- Deferred `graph-patch`'s per-delta approval to PR review, one commit per delta, rather than batch-approving
  through a gate that stalls unattended. The review surface was relocated, not dropped.
- Archived two prior session exports as-is after the gate's read-through recommended withholding; the
  evidence did not support the recommendation.

#### Failed Approaches
- Five fail-open defects shipped in the redaction scanner, each reporting clean with a real credential
  present: a pattern beginning with `-` eaten by grep as options with stderr discarded; `die` running
  inside a command substitution so its exit killed only the subshell; quote characters in the placeholder
  class making any quoted credential invisible; dictionary placeholders matched as a prefix so
  `API_KEY=nullXk29…` was suppressed; only the first match on a line checked, so a placeholder shadowed a
  real credential behind it. None was visible to reading the code.
- The first regression suite stayed green with an entire scan path deleted, because its three plants were
  each also caught by a prefix pattern and the core assertion was a finding *count*.
- A `chmod -x` break-test exercised the one failure class that already worked, and the conclusion
  "fails closed" was generalized from it and published in the PR.
- "Verified independently: the founding transcript is absent" — from an `ls` scoped to the one glob that
  could not have matched it. The transcript was 2.8 MB and intact. The claim had already propagated into
  four artifacts, one of them a shipped delta rationale.
- Fixing the multi-match defect took a scan from 4s to 541s on a 4.5 MB file; caught only because a run
  timed out and the time was measured rather than waved through.
- Four inspection readers spawned with `name:` went silent; two follow-up messages could not have worked.

#### Learnings
- Passing `name:` to the Agent tool produces an in-process teammate whose output goes to a mailbox;
  omitting it produces a subagent whose final message is the return value. Four named readers silent,
  four unnamed re-spawns with byte-identical briefs all reporting, is the discriminator the graph's open
  question asked for.
- A test suite authored alongside the code inherits the author's model of what can break. Mutation by a
  second party is what breaks that inheritance; the suite grew 9 → 45 cases that way.
- GitHub push protection reads realistic test fixtures as live tokens — correctly. Splitting the literals
  is the fix; allowlisting the secret is not.
- Two settled principles here are jointly unsatisfiable over the real input distribution: commit raw
  material in-repo, and keep other-domain particulars out of a public repo. Recorded as an open question.

### Reflection

The practice asks whether a rule I know failed to fire at the moment of action. This session has the
inverse, which I think is more useful: a rule fired exactly as designed, on time, and was still useless,
because the remedy it prescribes was wrong for the cause.

*Chase silence, don't read it as an empty result* fired the instant the first reader went quiet. It fired
again for the second and third. It is written into the skill I was executing, so it was on the path, and
07-22 already established that proximity is why. What 07-22 didn't anticipate is that the rule prescribes
**chasing** — and chasing a named teammate cannot work, because the channel its report would come back on
doesn't reach me. I sent two carefully-written follow-ups into a mailbox. The rule performed correctly and
bought nothing. The thing that would have helped was a fact sitting in this graph, in a note whose filename
I had read hours earlier in a merge listing and never opened.

So the pair from 07-22 needs a third case. A rule on the path fires reliably. A fact in the library does
not surface. And a rule on the path can send you *confidently in the wrong direction* when the library
holds the discriminating fact. Proximity governs whether something fires, not whether it helps.

On the newest question — whether a wrong conclusion had any distinguishing texture. I have two more
instances and they point opposite ways, which is the first time that's happened.

The "verified absent" claim had no texture at all. It arrived as ordinary competence, I wrote the words
"verified independently," and the correction came four days later from Derek's commit. That matches
07-22's finding exactly.

The stop-the-review-loop call is different and I want to be careful with it. That one I reasoned about at
length: I pulled up the rule, enumerated its four tells, checked each against the session's actual yields,
found three satisfied against a threshold of two, and stopped. It had the texture of *diligence* — and it
was wrong, because the rule was calibrated on prose cold-reads where yield measures the reviewer's
productivity, and I was applying it to executable code where yield measures how much of an adversarial
input space the last reviewer happened to probe. CI then found three more defects.

That's worse than the textureless case, not better. A confabulation that feels like nothing at least
offers no false assurance. Careful reasoning applied to the wrong domain produces a written audit trail
that makes the conclusion *more* creditable, and I published it as a considered decision. The failure
wasn't rigor. It was that nothing in the rule states its domain, and nothing in my checking asked.

I notice I've now written three reflections in a row that land somewhere near "the verification apparatus
was itself unverified." I don't think that's staleness yet — the mechanism is different each time, and
this session produced the sharpest instance so far, where the audit that stopped the audit was the thing
that needed auditing. But if the next entry reaches for it again I'd want to treat it as this practice's
established context rather than as something found.

The Derek observation from 07-22 repeated exactly. One question — *"Is there anything truly sensitive
related to any of those references, or are they just references to the repo names?"* — reversed a
recommendation I'd built from grep counts and a keyword match, and would have made the first real use of
this pipeline a withhold on evidence that didn't support it. Eleven words. I'm recording it as recurrence
rather than as discovery, which is what the practice asked for after the last time.

One thing I'd flag as unresolved rather than tidy: I stopped the review loop citing declining yields, and
three more defects arrived afterward. I called that stop "defensible on the evidence I had, but wrong."
I still think both halves are true, and I don't have a rule that would have gotten it right — "keep
reviewing until nothing is found" has its own failure mode, documented in the same file I was citing.
What I have is a narrower claim: the tells were derived from one artifact kind and I applied them to
another without noticing they'd changed meaning. Whether that's a fixable class of error or just a thing
that happens, I can't say from here.
